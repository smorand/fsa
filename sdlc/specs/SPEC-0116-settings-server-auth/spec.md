## 1. Summary
Two more sections of the YAML configuration, `server` (listen address, MCP path, public base URL) and `auth` (the public keys that verify callers' tokens, the token rules, the platform administrators), become settings a platform administrator reads and changes with the tools, the routes and the screen of SPEC-0114. A bad key is refused before it is saved, because a stored bad key would lock every caller out; a private key is refused and never echoed. The server reads both sections at the next start, listens where the stored section says, and verifies tokens with every stored key, so two keys can be accepted while a key is rotated. A server started with nothing but the admin database URL and the master key serves, with its auth taken from the database. A start with no key anywhere refuses to serve. In the same part, the names of the environment variables that hold a secret read at use (the git provider client secrets, the OCR key, the embedding key, the reranking key) are restricted: a master name can no longer be named, which closes an exfiltration path opened by SPEC-0114 and SPEC-0115.

## 2. Current State (MANDATORY)
Eleven sections are settings since SPEC-0115. `server` and `auth` are read from the YAML file only. The listen address is decided before the stored settings are read, so even a stored `server` section could not move it. The auth section holds one key, given as the path of a file; a server whose path is empty or unreadable starts and rejects every token. A token is accepted with 30 seconds of clock skew, read from the configured header first and from the standard authorization header second. Five keys name an environment variable that holds a secret and accept any name: the two git client secret keys, the OCR key, the embedding key and the reranking key. The value is read at use and sent to the address of the same section (a git provider, an OCR endpoint, an embedding endpoint).

### 2.1 What users can do today
- Move the listen address, change the MCP path, add a public key or an administrator: edit the YAML file and restart (14.1 items 1 and 2).
- Rotate a key: replace the file; no two keys are accepted at once (14.1 item 3).
- Start with a database URL alone and get auth or a listen address from the database: impossible (14.1 item 4).
- Name any variable, including the master key variable, as the holder of one of the five secrets (14.1 item 7).

### 2.2 Specs governing this area
SPEC-0114 (store, rules, screen, boot, flags, and the extract and search sections holding the OCR, embedding and reranking keys), SPEC-0115 (git section, the provider secret variable names), SPEC-0099 (the variable names the server starts with), the identity rules of the original port (token header, 30 second skew, issuer, claim).

### 2.3 What is verified today
The identity rules by their tests (identifiers in 14.1); the configuration by its snapshot tests; the store by the SPEC-0114 and SPEC-0115 suites; the device flow, the OCR service and the embedding targets by their own tests.

## 3. Scope
### 3.1 In scope
- The sections `server` and `auth` in the list, get and set tools, the routes, the screen.
- The start: the listen address and the MCP path from the stored section, the keys and rules of the stored auth section, the YAML seed.
- The check of every key before saving, the guards against a change that would lock every caller out, the rotation with several keys.
- The refusal to start serving with no key at all.
- The names of the five secret variables: refusal at change (reserved names and the secret namespace), refusal at use of the master names, warning at start.
### 3.2 Out of scope, and why
- Applying a change without a restart: same rule as SPEC-0114, every consumer reads its section once at the start (AUTO-038). The listen address cannot move live.
- Generating keys from the settings: keys are still made by the key command; a key is public data given as text.
- The `infra` section and the stores: part 6.
- An allow list of origin or CORS: not asked.
- A lock out guard for a key file that is unreadable: unchanged, such a server still starts and rejects every token (reported).
- Reading refusals at use for names outside the secret namespace that a YAML file holds: such a name keeps working, as the owner asked (today's YAML files keep working unless they name a master name), with a warning at the start (FR-NEW-024). A name outside the namespace that a stored section holds is not used at the start (FR-NEW-034); the namespace rule of FR-NEW-018 closes every name a platform administrator can give through a tool from this release on.
- A platform administrator who stores a public key can have a token signed by the matching private key accepted as any member: this power comes with the section and is accepted; it is reported.
- Decision D-0116-5: the destination class (a platform administrator chooses the address that receives a secret the server holds) is not created or widened by this lot, each sink being settable before it (`doc_service`, `extract` and `search` by SPEC-0114, `git` by SPEC-0115, the provider registry by SPEC-0102, the converter registry by SPEC-0106): `git.gitlab_instance_url`, `git.hosts` mapped to `gitlab`, `doc_service.api.url`, `extract.ocr.endpoint`, `search.embedding.endpoint`, the provider registry endpoint, the URL of an http converter. It is pinned by E2E-184 to E2E-190, each read through the stand in's own channel (they stay green by design), and is not changed (the owner's instruction for this run is the variable names; the standard S-04 forbids new exposure, not the removal of an old one) and is reported with the full list as a proposal: a complete answer binds each secret to its destination, a design of its own.
- Commands named by `doc_service.cli.command` and `doc.pandoc_bin` run as the server: giving them is code execution by a platform administrator, a power given by SPEC-0114. Removing the twelve master names from the environment of those children would give a false assurance (the child runs as the server user and can read the server's memory, files and database), so no change is made; the guard of this lot is declared partial for that class and the power is reported to the owner (decision D-0116-2).
### 3.3 Constraints imposed by the context
YAML alone behaves as today, except that a serve with no key anywhere is refused (FR-NEW-011). The existing configuration tests, their recorded printed forms and the identity tests are not modified. The tool contract keeps its tool count; only descriptions that list the sections change.

## 5. Usage scenarios
### 5.1 Happy
- **S1** The administrator sets the listen host to `127.0.0.1` and the port to a free port: the answer says a restart is required; the running server still answers on its old address and nothing answers on the new one; after the restart it answers on the new address only.
- **S2** Rotation: the administrator gives the new public key next to the old one; after the restart a token signed by either key is accepted and a token signed by a third key is refused; later she gives only the new key and after the restart a token of the old key is refused.
- **S3** An operator starts with only the database URL and the master key: the stored keys, administrators, issuer and listen address are in force; a caller with a token signed by a stored key is served.
- **S4** The first start from a YAML file imports `server` and `auth` once; a later YAML edit does not change them.
- **S5** The administrator changes the name of the token header: after the restart that header is read first and the standard authorization header is still read.
### 5.2 Failures
- **F1** A key that is not a public key in PEM form, a private key, or a ninth key is refused with the message naming its position; a private key is never echoed; nothing is stored.
- **F2** A change that would leave no key, no administrator or no identity claim is refused, nothing is stored.
- **F3** A host that is not an address or a name, an MCP path without a leading slash, a public base URL without a scheme is refused, nothing is stored.
- **F4** A start with no key anywhere refuses to serve and says how to give one.
- **F5** A member who is not a platform administrator is refused on the tools, the routes and the screen.
- **F6** A stored section the checks refuse stops the start naming it.
- **F7** A secret variable name (one of the five keys) that is a master name, or outside the accepted form, is refused at change.
### 5.3 Edge
- **E1** A token expired for 20 seconds is accepted, one expired for 40 seconds is refused; the same for a token not yet valid.
- **E2** The configured header wins over the standard authorization header; with the header absent the standard one is read.
- **E3** A key given as a file path and keys given as a list are all accepted together.
- **E4** A YAML file that names a master name as a secret variable starts, with a warning, and the variable is never read; a lower case name from the YAML keeps working.

## 6. Functional requirements
### 6.1 New
- **FR-NEW-001** The sections `server` and `auth` are setting sections: the list names thirteen sections in this order: safety, api, extract, doc, sqlite, db, doc_service, search, git, web, context7, server, auth; the refusal of an unknown section names the same thirteen.
- **FR-NEW-002** A change to `server` is accepted only when the host is a host name or an IPv4 address (a host name is one or more labels separated by single dots, each label 1 to 63 ASCII letters (either case), ASCII digits or hyphens that does not start or end with a hyphen, the whole name at most 253 characters; four numbers separated by dots read as a name and are accepted whatever the numbers), the MCP path starts with `/`, and the public base URL is empty or starts with `http://` or `https://` (case sensitive; the scheme alone is accepted); a refusal says `invalid server.host '<value>': expected an IPv4 address or a host name`, `server.mcp_path must start with '/' (got '<value>')` (the words the start gives today), or `invalid server.public_base_url '<value>': must start with http:// or https://`; a port outside 1 to 65535 or of the wrong type is refused as FR-NEW-038 says; a refusal changes nothing, so `restart_required` is as before and the running server keeps its address.
- **FR-NEW-003** A change to `server` applies at the next start; the answer says `restart_required` while the stored section differs from the running one, and the running server keeps listening on the address it started with.
- **FR-NEW-004** At the start, a stored `server` section replaces the one from the YAML or the defaults: the server listens on the stored host and port and serves the MCP route at the stored path; the address in force is the stored one, whichever the file named.
- **FR-NEW-005** A change to `auth` is accepted only when every entry of `jwt.public_keys` is an RSA public key in PEM form; a refusal says `auth.jwt.public_keys[<position>] is not a public key in PEM form (an RSA public key is expected)` (position counted from 0), or `auth.jwt.public_keys[<position>] holds a private key: only a public key is accepted`, or `auth.jwt.public_keys holds more than 8 keys`; one bad entry stores none of the others; both the `-----BEGIN PUBLIC KEY-----` and the `-----BEGIN RSA PUBLIC KEY-----` forms of an RSA key are accepted, an EC key, a certificate and any other label are refused with the first message; a key repeated, and a key followed by blank lines, are accepted and stored as given; an entry is a private key as FR-NEW-041 says, which is checked first and gives the private key message; an entry that holds more than one PEM block, or text other than blank lines around one block, gives the first message; a line made only of spaces, tabs or a carriage return is a blank line, a key written with CRLF line endings is accepted and stored as given, and a space or tab before `-----BEGIN` or after `-----END` and its closing dashes on the same line gives the first message.
- **FR-NEW-006** A change to `auth` is refused when it would take away what the section holds now: when the section holds a key (a non empty `jwt.public_keys` or `jwt.public_key_path`) and the result holds none, with `auth.jwt needs at least one public key: give public_keys or public_key_path`; when it holds an administrator and the result holds none, with `auth.admins needs at least one platform administrator`; or when it holds an identity claim and the result holds an empty one, with `auth.jwt.username_claim must not be empty` (a section that holds none of these now is not refused for staying so, which keeps a change of another key possible); when a change breaks several rules of FR-NEW-005 and FR-NEW-006 the refusal reports the first in this order: the form of a key (lowest position first), the number of keys, no key, no administrator, empty identity claim.
- **FR-NEW-007** The server accepts a token signed by any key of the stored list and by the key of the file named by `jwt.public_key_path`, all at once; a token signed by another key is refused; a key removed from the list is no longer accepted after the next start.
- **FR-NEW-008** A token is accepted up to 30 seconds after its expiry and 30 seconds before its start time, and refused beyond, whatever the source of the key (file or database).
- **FR-NEW-009** The token is read from the header named by `jwt.header` first and from the standard `Authorization` header second; when the first holds a `Bearer` credential, a `Basic` credential with a password, or a text with no space, that credential alone is verified, and a failure refuses the call as not authenticated even when the second holds a valid token; when the first is absent or holds none of those forms the second is read; the forms are those the server accepts today (`Bearer` or `bearer` followed by a space and the token, `Basic` or `basic` followed by a space and the base64 text of `user:password`, where the password is not empty and is the token, or a text with no space), any other spelling of the scheme counts as none of them; this holds for the stored header name as for the default.
- **FR-NEW-010** At the start, a stored `auth` section replaces the one from the YAML or the defaults: its keys, administrators, issuer, audience, identity claim, header and algorithm list are those in force; a server started with a database and no YAML serves callers with a token signed by a stored key, and a person is an administrator when the stored list names her.
- **FR-NEW-011** The server refuses to start serving, and binds no address, when after the stored settings are applied it holds no key (an empty list and an empty file path), with `no auth key is configured: store auth.jwt.public_keys or set auth.jwt.public_key_path (a first start from a YAML file imports them)`; building the application without serving it, and a path to a file that cannot be read, are unchanged.
- **FR-NEW-012** A stored `server` or `auth` section the checks refuse stops the start with `the stored settings are refused: <message>` naming the failing rule; a stored section the server cannot read stops it with `the stored setting '<section>' is unreadable`; a stored section that is not a set of named values, or a set holding a value of the wrong type (a port that is not a whole number from 0 to 65535, a text port, a `public_keys` that is not a list of texts), stops it with `the stored setting '<section>' is invalid: the value of '<key>' has the wrong type` (`<key>` is the first wrong typed key in the alphabetical order of FR-NEW-014; a port that is not a whole number from 0 to 65535, `70000`, `-1` and `3.5` included, is a wrong typed `port`), or, for a section that is not a set of named values, `the stored setting '<section>' is invalid: the value has the wrong type`.
- **FR-NEW-013** The two sections hold no secret value: a private key is refused and its text never appears in an answer, a change record, a refusal message or a stored row; a read answers the public keys as given and `secrets` as an empty object.
- **FR-NEW-014** The change record holds the names of the changed keys only, never a value: `jwt.public_keys`, `admins`, `host`, `port`, and so on, written in ascending alphabetical order of the dotted name (`admins`, `host`, `jwt.algorithms`, `jwt.audience`, `jwt.header`, `jwt.issuer`, `jwt.public_key_path`, `jwt.public_keys`, `jwt.username_claim`, `mcp_path`, `port`, `public_base_url`); a refused change adds no line; an accepted change that changes nothing adds one line with no key.
- **FR-NEW-015** A start from a YAML file imports each of the two sections that has no row, once, by `system:yaml`; a later YAML edit is ignored while a row exists, with the warning of SPEC-0114; a YAML alone start behaves as before, and the printed form of a YAML section with no `public_keys` is unchanged (the recorded snapshots of the existing configuration tests); `jwt.public_keys` is accepted in a YAML file and a bad form, a private key or more than 8 entries there stops the start with the same message as a change, while a key under 2048 bits or over 8192 bits starts (FR-NEW-026 and FR-NEW-045 are for a change only); such a key verifies no token, as today.
- **FR-NEW-016** Reading, listing and changing the two sections, by tool and by route, and the screen, are for platform administrators; the screen lists and edits them like the eleven others and shows a refusal.
- **FR-NEW-017** The behavior is the same on SQLite and on PostgreSQL.
- **FR-NEW-018** A change that gives one of the five keys that name a secret variable (`git.github_client_secret_env`, `git.gitlab_client_secret_env`, `extract.ocr.api_key_env`, `search.embedding.api_key_env`, `search.reranking.api_key_env`) is checked in this order. (1) A name that is `FSA_TOKEN_KEY`, `MCPFS_TOKEN_KEY`, `FSA_DATABASE_URL`, `FSA_MINIO_ACCESS_KEY`, `FSA_MINIO_SECRET_KEY`, `FSA_META_DSN`, `MCPFS_META_DSN`, `MCPFS_ADMIN_DSN`, `MCPFS_GIT_DSN`, `MCPFS_OAUTH_DSN`, `FSA_DOC_SERVICE_TOKEN` or `MCPFS_DOC_SERVICE_TOKEN` is refused with `<section>.<key> '<name>' names a variable reserved by the server, it cannot hold a secret` (`<section>.<key>` is the dotted key as written above, for example `git.gitlab_client_secret_env`). (2) Otherwise a name is accepted only when it is one of the default names of that key (`FSA_GITHUB_CLIENT_SECRET` and `MCPFS_GITHUB_CLIENT_SECRET` for `git.github_client_secret_env`, `GITLAB_CLIENT_SECRET` for `git.gitlab_client_secret_env`, `FSA_OCR_KEY` and `MCP_FS_OCR_KEY` for `extract.ocr.api_key_env`, none for the other two) or is `FSA_SECRET_<SINK>_` followed by one or more capital letters, digits or underscores (the ASCII letters A to Z and the ASCII digits 0 to 9), where `<SINK>` is `GITHUB` for `git.github_client_secret_env`, `GITLAB` for `git.gitlab_client_secret_env`, `OCR` for `extract.ocr.api_key_env`, `EMBEDDING` for `search.embedding.api_key_env` and `RERANKING` for `search.reranking.api_key_env` (so a name made for one key is not accepted for another); any other name is refused with `<section>.<key> '<name>' is not an accepted variable name: use FSA_SECRET_<SINK>_ followed by capital letters, digits and underscores` (`<SINK>` spelled out for the key, for example `use FSA_SECRET_GITLAB_ followed by capital letters, digits and underscores`). A null name is accepted for `git.github_client_secret_env` and `extract.ocr.api_key_env` and an empty name for the embedding and the reranking keys (no variable); an empty name for the first two, a null name for the embedding and the reranking keys, and a null or empty name for `git.gitlab_client_secret_env` are refused with the second message (the name shown is `''`). A value that is not a text, and not null where null is accepted, is refused with a message that begins `invalid setting '<section>':` (the type refusal of the section), not with the second message. A change that does not give the key is not refused for the value already stored. When a change gives several of the five keys they are checked in the order `git.github_client_secret_env`, `git.gitlab_client_secret_env`, `extract.ocr.api_key_env`, `search.embedding.api_key_env`, `search.reranking.api_key_env`, the first refusal is reported, and these checks run before every other check of the same change. Nothing is stored on a refusal.
- **FR-NEW-019** The server never reads `FSA_TOKEN_KEY`, `MCPFS_TOKEN_KEY`, `FSA_DATABASE_URL`, `FSA_MINIO_ACCESS_KEY`, `FSA_MINIO_SECRET_KEY`, `FSA_META_DSN`, `MCPFS_META_DSN`, `MCPFS_ADMIN_DSN`, `MCPFS_GIT_DSN`, `MCPFS_OAUTH_DSN`, `FSA_DOC_SERVICE_TOKEN` or `MCPFS_DOC_SERVICE_TOKEN` as one of the five secrets, whatever put the name in the configuration (a change, a YAML file or an operator's edit of the database); the names a change may no longer give (FR-NEW-018 (2)) but that an earlier release stored, or that a YAML file holds, are not refused at use, which keeps today's YAML files working: a device flow whose name is one of the twelve master names answers `<Provider> client secret variable '<name>' is not allowed: the server reserves it` (`GitHub` or `GitLab`) and sends nothing to the provider; an OCR read answers `OCR key variable '<name>' is not allowed: the server reserves it` and sends nothing to the OCR endpoint; an embedding call answers `Embedding key variable '<name>' is not allowed: the server reserves it` and sends nothing; a start whose configuration names one logs the warning `<section>.<key> names the reserved variable '<name>': the server will not read it as a secret` (with `<section>.<key>` as in FR-NEW-018) and still starts; each of the three refusals at use is `ERR_INVALID_ARGUMENT`; any other name that a YAML file holds, including one outside the accepted form of FR-NEW-018, keeps working (a name that a stored section holds and that is not a master name is judged by FR-NEW-034, a stored master name by FR-NEW-036).
- **FR-NEW-022** A change to `auth` whose `jwt.public_keys` is not a list of texts, whose `admins` is not a list of texts, or which holds any value of the wrong type, is refused as FR-NEW-043 says; a change that leaves an entry of `admins` empty, `jwt.header` empty or `jwt.algorithms` empty is refused with `invalid setting 'auth': admins must not hold an empty name`, `invalid setting 'auth': jwt.header must not be empty` or `invalid setting 'auth': jwt.algorithms must not be empty`; an algorithm name the build cannot verify is accepted at a change (it is warned at the start, as today); a repeated administrator is stored as given; nothing is stored on a refusal.
- **FR-NEW-020** At the start, a stored `server` section is checked for host, MCP path and public base URL (FR-NEW-002) and a stored `auth` section for the form and the number of keys (FR-NEW-005); a YAML file is checked for its MCP path, as today, and for the keys of its `auth` section, so a YAML file written for the previous release keeps loading and building whatever its host and public base URL hold (binding the address is the operator's matter, as today); the port range, the guards of FR-NEW-006 and FR-NEW-022 the key size of FR-NEW-026 and the form of the secret variable names of FR-NEW-018 (2) are checked at a change only, so a YAML or stored port `0` (the system picks a free port), an empty administrator list or a lower case secret variable name does not stop the start.
- **FR-NEW-021** The start banner names the host and port in force after the stored settings are applied, and the origin of the configuration, in the present form `Serving fsa <version> on <host>:<port> (config=<origin>)` where `<origin>` is the file path or `none, settings from the database`; it is printed once the stored settings are applied and before the key check of FR-NEW-011, so a start refused for lack of a key has printed it, then prints the refusal and exits with a failure status.

- **FR-NEW-023** When a change to `server` or `auth` holds several values of the wrong type, the refusal is the one of FR-NEW-043 for the first such key; the port rule is FR-NEW-038. When a change to `server` breaks several other rules, the refusal reports the first in this order: a value of the wrong type, the public base URL change refused by FR-NEW-042, the host, the MCP path, the form of the public base URL, the port. When a change to `auth` breaks several other rules, the refusal reports the first in this order: a value of the wrong type, an empty entry of `admins`, an empty `jwt.header`, an empty `jwt.algorithms`, then the order of FR-NEW-006 (the form of a key by position, the size of a key (FR-NEW-026), the number of keys, no key, no administrator, empty identity claim). When both stored sections are refused at the start, the one that comes first in the section list of FR-NEW-001 is named.
- **FR-NEW-024** At the start, for each of the five keys whose configured name is not one of its default names, not in the secret namespace and not a master name, the server logs once `<section>.<key> names '<name>' outside the secret namespace: it is still read as a secret, prefer a name starting with FSA_SECRET_` (the name only, never the value) and still starts; a null or empty name (no variable) logs nothing.

- **FR-NEW-025** While the list in force (the stored one, or the one of the YAML file while no value is stored) holds at least one key and the file named by `jwt.public_key_path` cannot be read or does not hold an RSA public key in PEM form, the server starts, accepts tokens signed by a key of the list, refuses a token that only the key of that file would verify, and logs once per start `auth.jwt.public_key_path '<path>' cannot be read as an RSA public key: it is ignored`.
- **FR-NEW-026** A change to `auth` whose `jwt.public_keys[<position>]` is an RSA public key with a modulus under 2048 bits is refused with `auth.jwt.public_keys[<position>] holds an RSA key shorter than 2048 bits`; this check comes after the form check of FR-NEW-005 and before the number of keys is judged by FR-NEW-006, and it is made at a change only, so a key already stored or held by a YAML file starts (it verifies no token, as today, the token library accepting RSA keys from 2048 to 8192 bits only); nothing is stored on a refusal.

- **FR-NEW-027** In a change to `auth`, an entry of `admins`, the value of `jwt.header`, an entry of `jwt.algorithms`, the value of `jwt.username_claim` and the value of `jwt.public_key_path` count as empty when they hold no character, or only white space (spaces, tabs, carriage returns, line feeds and the other white space characters); the first four are then refused with the messages of FR-NEW-022 and FR-NEW-006 for an empty value, and a path of that kind counts as no path for the no key rule of FR-NEW-006; any other value is stored as given, without trimming.

- **FR-NEW-028** At the first start from a YAML file, a `server` section whose host or public base URL fails FR-NEW-002 is not imported, and the start logs once `the YAML section 'server' is not imported: <message of FR-NEW-002>`; the YAML section stays in force at every start while no value is stored, and no import line is recorded for it; a later change to `server` is judged on the whole section as it will be, so it is refused until the host and the public base URL are valid.
- **FR-NEW-029** The checks of FR-NEW-005 on the form of a key and of FR-NEW-026 on its size apply, at a change, only to the entries of `jwt.public_keys` given in the change: a change that does not give `jwt.public_keys` is not refused for the keys already stored; the rule on the number of keys (more than 8) and the no key rule of FR-NEW-006 apply to the list as it will be.
- **FR-NEW-030** Every read of `auth` holds `jwt.public_keys` as a list of texts (`[]` when none) and `jwt.public_key_path` as a text (the empty text when none), whether the section is stored, imported or never set.

- **FR-NEW-031** At the first start from a YAML file, an `auth` section that holds no key (an empty `jwt.public_key_path` and an empty `jwt.public_keys`, or no `auth` block at all) is not imported and the start logs once `the YAML section 'auth' is not imported: it holds no key`; the YAML section stays in force while no value is stored, so a later YAML edit that adds a key is read and imported at the next start.

- **FR-NEW-032** When several stored sections fail at the start, whatever the kind of failure (unreadable, invalid, refused), the start names the one that comes first in the section list of FR-NEW-001.
- **FR-NEW-033** The limit of 8 keys counts every entry of `jwt.public_keys` as given, a repeated key included.

## 7. Non functional requirements
Every refusal of FR-NEW-002, 005, 006, 018 and 022 is `ERR_INVALID_ARGUMENT`, as the refusals of SPEC-0114. Security and access: platform administrators only, reading included (SPEC-0114); no key material beyond public keys is stored or returned. Reliability: a refusal comes before any write, so a bad value never reaches the database; a stored value the start refuses stops the start naming it. Compatibility: a YAML file written for the previous release loads unchanged. Operability: a repeated YAML difference logs one warning, as in SPEC-0114.

## 8. Edge cases
An empty public key list with a file path set; two equal keys in the list; a key with trailing blank lines; the host `0.0.0.0` and `localhost`; a path `/` alone; an empty public base URL; a stored section with missing keys (takes the defaults, not the YAML, as SPEC-0115); two administrators saving at once (last write wins, both recorded, SPEC-0114); a stored algorithm name the build cannot verify (warned at the start, as today, not refused).

## 12. Glossary
Section: one top level block of the configuration. Public key list: the PEM texts that verify tokens. Key file: the single key named by a path, as today. Running section: the one the process was started with. Seed: the one time import of the YAML. Master names: the twelve variables that the server reads, that its documentation and templates name, or that an earlier plan gave to the stores' DSN: `FSA_TOKEN_KEY`, `MCPFS_TOKEN_KEY`, `FSA_DATABASE_URL`, `FSA_MINIO_ACCESS_KEY`, `FSA_MINIO_SECRET_KEY`, `FSA_META_DSN`, `MCPFS_META_DSN`, `MCPFS_ADMIN_DSN`, `MCPFS_GIT_DSN`, `MCPFS_OAUTH_DSN`, `FSA_DOC_SERVICE_TOKEN` and `MCPFS_DOC_SERVICE_TOKEN`, never read as a secret. Secret namespace: for each of the five keys, the names `FSA_SECRET_<SINK>_` followed by capital letters, digits or underscores, the only names besides the defaults that a change may give to that key.
